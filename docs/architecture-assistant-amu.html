Qui fait quoi, et qui appelle qui

Cette page décrit la structure du code, non les concepts du RAG — ceux-ci sont traités par la page pédagogique. Elle répond à trois questions : de quels modules le projet est fait, dans quel ordre ils s'appellent lorsqu'une requête arrive, et de quoi chaque classe est responsable. Les diagrammes sont générés depuis leur source textuelle : hors ligne, celle-ci s'affiche à leur place.

00

Quatre couches, une seule direction de dépendance

Le paquet src/assistant_amu se lit en quatre couches. Chacune ne connaît que celles situées en dessous d'elle : aucune couche basse n'importe une couche haute, ce qui permet d'employer l'ingestion ou la recherche sans monter l'API.

Les flèches se lisent « importe ». Aucune ne remonte.

Deux modules n'importent rien du projet. retrieval/embedder.py et generation/rewrite.py reçoivent ce dont ils ont besoin en paramètre — un nom de modèle pour l'un, un backend pour l'autre. C'est ce qui permet de les tester sans base vectorielle ni appel réseau, et de rejouer une expérience d'évaluation sur un encodeur différent sans toucher au reste.

02

Chaîne d'ingestion hors ligne

Du fichier corpus/sources.yaml à la collection ChromaDB. Cette chaîne s'exécute à la demande, jamais pendant une requête utilisateur.

  Y["corpus/sources.yaml"] --> D["download.download_all
robots.txt, délai 1 s"]
  D --> RAW[("corpus/raw/")]
  RAW --> E["extract.extract
pdfplumber → docling
beautifulsoup4"]
  E --> C["clean.clean_document
boilerplate, sommaires"]
  C --> K["chunk.chunk_document
≤ 500 tokens, chevauchement 50"]
  K --> A["VectorStore.add_chunks"]
  A --> EM["Embedder.embed_passages
préfixe « passage: »"]
  EM --> DB[("ChromaDB
cosinus")]
  E -. document scanné .-> X["exclu et signalé"]

Orchestration : ingestion/pipeline.py · commande : python -m assistant_amu.ingestion index

L'exclusion est un résultat, pas une erreur. Un PDF scanné lève ScannedDocumentError, que ingest_corpus capture pour l'inscrire au rapport. Une source illisible n'interrompt jamais le lot.
03

Chaîne d'appel d'une requête /ask

Le trajet complet d'une question, de la requête HTTP à la réponse sourcée. Les deux sorties anticipées — aucun passage récupéré, refus du modèle — sont ce qui garantit qu'une réponse sans source ne cite jamais de source.

sequenceDiagram
  autonumber
  participant C as Client
  participant A as api/main.ask
  participant P as RagPipeline
  participant S as VectorStore
  participant E as Embedder
  participant B as LLMBackend
  C->>A: POST /ask {question, k, history?}
  A->>P: answer(question, k, history)
  P->>P: prepare() → condensation, réécriture
  P->>S: query(retrieval_query, k)
  S->>E: embed_queries(« query: » + question)
  E-->>S: vecteur
  S-->>P: liste de RetrievedChunk
  alt aucun passage
    P-->>A: RagResult(refus, sources vides)
  else passages trouvés
    P->>P: build_user_message(question, sources)
    P->>B: generate(prompt système, message)
    B-->>P: réponse
    alt réponse = refus canonique
      P-->>A: RagResult(refus, sources vides)
    else réponse ancrée
      P-->>A: RagResult(réponse, sources)
    end
  end
  A-->>C: AskResponse {answer, sources[], model, …}

Le refus vide la liste des sources dans les deux cas : citer un passage qu'on n'a pas utilisé induirait en erreur.

Un appel de modèle économisé. Lorsque la recherche ne remonte rien, le pipeline refuse sans appeler le backend. C'est la branche « aucun passage » du diagramme : elle coûte zéro token.
04

Conversation multi-tour : où la question est réécrite

Deux transformations peuvent s'appliquer à la question avant la recherche. Elles sont résolues au même endroit, RagPipeline.prepare, pour que l'aperçu affiché à l'utilisateur et la requête réellement cherchée ne puissent pas diverger.

flowchart TB
  Q["question de l'utilisateur"] --> H{"history
fourni ?"}
  H -- non --> BQ["question inchangée"]
  H -- oui --> CD["_condense
appel backend · condense_system.md"]
  CD --> BQ
  BQ --> RW{"rewrite ?"}
  RW -- "raw (défaut)" --> RQ["requête de recherche"]
  RW -- strip --> ST["strip_query
retrait de l'ouverture · aucun appel"]
  RW -- llm --> LR["rewrite_query
appel backend"]
  ST --> RQ
  LR --> RQ
  RQ --> S["VectorStore.query"]

Sans historique et en mode raw, les deux branches sont l'identité : le comportement mono-tour est reproduit à l'exact.

La rétrocompatibilité est une propriété du chemin, pas une promesse. Aucune des deux transformations ne s'applique par défaut ; une requête sans history et sans rewrite traverse prepare sans qu'aucun appel de modèle supplémentaire soit émis.

06

Erreurs et refus : deux mécanismes distincts

Un refus et une panne se ressemblent pour l'utilisateur : dans les deux cas, il n'obtient pas de réponse. Le code les traite pourtant par deux chemins séparés, et c'est volontaire — l'un est un résultat attendu, l'autre un incident.

flowchart TB
  subgraph R["Refus — résultat attendu"]
    direction LR
    R1["is_refusal(réponse)"] --> R2["sources vidées"] --> R3["HTTP 200"]
  end
  subgraph F["Panne — incident"]
    direction LR
    F1["httpx lève"] --> F2["_map_http_error
cause normalisée"] --> F3["LLMBackendError"] --> F4["HTTP 503"]
  end
Le refus se compare, il ne se devine pas

La phrase de refus du prompt système est comparée après normalisation — minuscules, ponctuation retirée, espaces réduits — et non caractère par caractère. Un modèle qui ajoute un point final produit toujours un refus reconnu.

Une requête échoue vite

Aucune reprise n'est tentée pendant /ask : une panne remonte immédiatement en 503. La reprise avec attente progressive existe, dans backoff.py, mais elle sert aux traitements par lots, où réessayer a du sens.

Ce qui vit à côté du pipeline

Trois travaux sont mesurés et documentés sans être intégrés à /ask. Sur le plan du code, cela se voit : ils consomment les briques de recherche sans qu'aucune ligne du pipeline ne les appelle.

Une nuance sur la réécriture. Elle est le seul de ces travaux dont le code se trouve dans le paquet de production, parce que /ask l'expose en option. Le défaut reste raw, c'est-à-dire l'identité : le comportement par défaut du pipeline n'en est pas affecté.

Les chiffres de ces mesures, leurs limites et leurs conditions figurent dans docs/mesures.md. Cette page ne dit que où le code se trouve.
